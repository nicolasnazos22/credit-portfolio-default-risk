# Servicio de Scoring Crediticio
* Descarté el uso de un script imperativo para el cálculo de riesgo crediticio en favor de un componente reutilizable que encapsula el modelo y su estado en memoria.
* El estado del servicio está compuesto por los predictores cargados desde archivos .joblib (modelo entrenado y vector de coeficientes)
* Los beneficios  de esta decisión son: 
* 1. Carga única del modelo en memoria: el modelo se carga una sola vez al inicio de la sesión, evitando operaciones repetidas de lectura desde disco y reduciendo la latencia de inferencia en requests posteriores. Incluso en entornos cloud, las operaciones de I/O siguen siendo significativamente más costosas que el acceso a memoria. Este diseño mejora el throughput del servicio minimizando operaciones de I/O
* 2. Uso de reindex para forzar la consistencia del esquema de features entre entrenamiento e inferencia. Esto garantiza que los datos de la request se alineen con la estructura esperada por el modelo, independientemente del orden del JSON. Además, permite manejar features faltantes asignándoles un valor por defecto (0), reduciendo errores en producción. Esta imputación por defecto tiene como finalidad mantener la integridad del vector de entrada sin romper la inferencia.
* 3. En lugar de hardcodear rutas, utilizo Pathlib para definir ubicaciones relativas a la raíz del proyecto. Esto hace que el código sea agnóstico al sistema operativo, lo que permite su ejecución en Windows o Linux (por ejemplo en Docker) sin modificaciones en la configuración.
* Realicé un refactor sumnando lógica de negocio: etiquetado de riesgo a partir de los umbrales definidos en el archivo .config/variables de entorno.
* También moví la predicción de default a este microservicio, para eliminar completamente la lógica de negocio del archivo de schemas.
* Explicabilidad agregada al service de scoring crediticio. Detalles interesantes de la implementación:
* 1. Se carga en memoria el TreeExplainer de la librería shap. Esto permite cargarlo una sola vez en RAM al levantar la api, lo que  es clave para maximizar el throughput y minimizar la latencia. Veamos, para entenderlo, por qué este paso es necesario:
* 1. 1. l constructor del TreeExplainer no es trivial: tiene que parsear la estructura interna del modelo (árboles, splits, valores de hoja) y armar las estructuras necesarias para calcular SHAP values de forma eficiente. Ese costo se paga una sola vez si lo dejás en memoria.
1. 2. El problema de lo anterior no es sólo tener el modelo en disco. Es lo que implica tener que reinstanciar al constructor del Tree Explainer. Si no estuviera cargado en RAM  habría que des-serializarlo, reconstruir el objeto python y volver a inicializar Shap con cada request. Esto claramente tiene un overhead de latencia y no escala.
1. 3. Finalmente notemos que en caso de escalar horizontalmente y haber múltiples workers (gunicorn+guvicorn) cada worker cargaría su propia instancia del TreeExplainer en RAM, evitando compartir memoria entre procesos. Esto último es particularmente interesante porque:
1. 3. 1. Tener procesos independientes implica priorizar aislamiento de fallos y estabilidad por sobre optimización de memoria. En este contexto es vital: un problema (crash por ejemplo) de un worker no afecta a los otros.
1. 3. 2. Se evita problemas de concurrencia. Notemos que shap no es thread safe en inferencia concurrente. El tree explainer mantiene estado interno mutable durante el cálculo de los valores SHAP. Con esta decisión el costo que pagamos para no lidiar con deadlocks, accesos concurrentes a recursos, etc (que efectivamente pueden ocurrir debido a que los threads compartirían ese estado mutable) es mayor uso de RAM. Esto implica necesariamente que, en el escalado horizontal, va a haber que limitar la cantidad de instancias paralelas que se levanten de la api para no disparar el costo.
1. 3. 3. En servig de machine learning se escala horizontalmente con procesos porque en CPython el GIL  limita el paralelismo a nivel de threads.
* Refactor de servicio de scoring: el problema del servicio es que básicamente es una superclase y viola el principio de responsabilidad única. Me di cuenta de que básicamente la clase tiene varias responsabilidades diferentes: clasificar la probabilidad en baja, media y alta, correr el algoritmo shap, predecir. Es demasiado. Lo ideal para promover el máximo desacoplamiento 
y poder testear con mayor facilidad cada componente es que cada clase tenga una y solo una responsabilidad. Más info en refactor-service.
