# Estrategia de testing:
* Mi estrategia de testing del motor de credit scoring se basa en que el dominio es matemático, lo que implica que el sistema debe cumplir ciertas propiedades matemáticas.
* Por eso mismo recurro a property-based testing: el espacio muestral a testear es enorme, entonces es más fácil delegar a la máquina la generación de casos mediante Hypothesis que pensar en casos puntuales.
* En ese sentido, la clave del property based testing es: "decime las propiedades que debe cumplir el sistema y yo voy a tratar de encontrar el input que las destroce".
* Esta idea deriva de un concepto clásico en algoritmia: **invariante**. Esta es una propiedad que se debe cumplir en todo momento para que el algoritmo sea correcto.
* Si un invariante es violado eso quiere decir que el algoritmo tiene problemas lógicos y hay que revisarlo.
* Hypothesis en particular permite definir estrategias para generación de casos de prueba. Prueba múltiples combinaciones de acuerdo a los tipos de datos definidos en la estrategia y no valores puntuales. Es fundamental no olvidar que 
las pruebas unitarias no garantizan la corrección total del sistema, solo reducen la probabilidad de que el sistema falle.
* Separando la generación de casos de prueba del enunciado de la propiedad que el sistema no debe violar nos aseguramos de que la máquina busque edge cases que la rompan. 
* Hypothesis en ese sentido está muy bien pensado: al encontrar un input que rompe una propiedad busca el valor mínimo que la viola. Notemos que esto facilita encontrar las fallas, y en consecuencia aumenta la productividad del equipo.
* Otra parte de mi estrategia de testing consiste en desacoplar la generación de clientes para los casos de prueba y las estrategias de las propiedades en sí.
* Generar los casos de prueba a partir de la lógica desacoplada del dominio definido en el yaml me permite usarlas en los componentes cuando sea necesario inyectar clientes en lugar de hardcodear la definición del tipo de dato en cada archivo.
* La idea deriva del patrón Factory y promueve desacoplamiento.  A su vez facilita la inyección de dependencias para testing ya que los clientes pueden generarse e inyectarse naturalmente.
* El esquema de generación de valores para los clientes a partir de los diferentes atributos definidos en el  YAML tiene en este momento una limitación clara: la resolución de dependencias se hace en dos pasadas, lo que funciona para dependencias simples pero no para grafos de profundidad arbitraria.
* Para realmente modelar esto como un DAG falta resolver las dependencias mediante orden topológico usando un algoritmo como Kahn, además de validar dependencias circulares al iniciar la aplicación. Queda como TODO para el próximo refactor.
* Como el scoringService recibe un JSON ya validado por el schema de Pydantic no necesito usar clientes inválidos. Los clientes inválidos los uso para después poblar un dataframe  que me sirva para testear el validador porque la validación es offline.
* Es importante explicar que en el caso del cliente inválido se busca violar exactamente una sola regla del YAML porque eso simplifica el aislamiento y la detección de bugs en producción.
* Una nota importante: en este caso decidí usar property-based testing porque la cantidad de casos posibles es enorme. Cuando los casos son pocos y se pueden enumerar fácilmente normalmente conviene más usar unit tests tradicionales
